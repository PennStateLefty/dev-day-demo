## Summary and recommendation

**Use `martaldsantos/claims-processing-hack` as the primary technical comparison baseline, not as a codebase to fork or merge wholesale.** It is an unarchived, MIT-licensed, end-to-end educational example spanning document processing, policy matching, API/workflow, MCP, evaluation/observability, and UI. Its content substantially overlaps the archived Microsoft repository, so prefer this one for current comparison and consult the archived source only for historical lineage. Validate individual dependencies, APIs, asset rights, and data syntheticity before reuse. Its repository-level MIT license has a copyright notice naming the maintainer, but the similarly MIT-marked Microsoft upstream carries that same copyright line despite the different repository identity; resolve that provenance discrepancy before reusing upstream material.

For potential synthetic policy/claim examples and Foundry learning patterns, review `lohithgn/foundry-insurance-agents-workshop` as a complement: its README explicitly describes fictional Northwind Mutual data and the repo has an MIT license. First verify that each specific file is synthetic and covered by the license; then select only a very small automotive-relevant sample. Do not import it during this checkpoint.

The `alipouw13/insurance-multi-agent` design is the strongest **conceptual multi-agent reference** for the event narrative: a supervisor coordinates specialist roles, with separate Foundry prompt-agent definitions in its newer path. Its role separation is more useful for the three-presenter story than a two-agent pipeline paired with a chat-only Copilot Studio UI. Use only the architectural idea; do not copy its code or prompt text. The repository owner has directed that it and `nstefanac1/ClaimsAgent` be treated as MIT for planning, based on the belief that they were generated by Microsoft staff. This is an **unverified working assumption**, not a license found in either repository: GitHub detected no license and no repository `LICENSE` file was present at the reviewed revisions. Staff affiliation or authorship alone does not establish MIT terms or grant redistribution rights.

The original `alipouw13` workflow is not a direct fit: its supervisor requires claim, policy, and risk specialists, optionally adds a claims-data analyst, and emits approve/deny/investigate recommendations. Its risk scoring, claimant-history analysis, and outcome language are out of scope. Its current code also contains two different agent-registration paths (prompt-agent definitions and a separate classic Agent Service path), so do not treat it as a ready-made pattern for a hosted-agent plus prompt-agent architecture. Rebuild a smaller workflow around a Foundry hosted orchestrator, prompt-based policy and response specialists, deterministic completeness checks, shared Foundry IQ grounding, and human review.

The licensed `jamespaultg/copilot-claim-retrieval-agent` is a reference for a low-code claims-status workflow, but its workbook, documents, images, and video require asset-specific rights and synthetic-data review; it is not a technical baseline for the claims-assessment slice.

## Cross-source findings

- The Microsoft archived repo and contributor-maintained repo are closely overlapping examples. Count their repeated policies, challenge flow, and claim examples once; do not merge both.
- The multi-agent reference is useful for conceptual role separation, not as an implementation baseline: its supervisor behavior and mixed agent-registration approaches do not match this demo's human-review and current Foundry requirements.
- The Foundry workshop is the clearest source that explicitly calls its example data synthetic. The other repositories require file-level review before treating any data as synthetic.
- Potential technology coverage includes Python/FastAPI, Foundry agents and evaluation, Azure AI Search, MCP, Streamlit, .NET labs, Next.js, Bicep, Azure Developer CLI, and Copilot Studio/Power Automate. These are examples, not a mandate to combine their stacks.
- No code/data was copied for this assessment. Candidate reuse decisions must be revisited after the first checkpoint review and current product/API validation.
